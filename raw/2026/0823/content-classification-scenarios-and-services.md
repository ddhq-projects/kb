## Классификация контента: сценарии, состав системы и подборка сервисов

## Вводные

Классификация контента нужна, чтобы автоматически превращать тексты, документы и AI-запросы в структурированные данные: темы, типы задач, уровни риска, отделы, проекты и действия. Это помогает быстрее искать материалы, считать usage/cost, модерировать контент и запускать автоматизации. Для AI-генераций первым стоит смотреть на OpenRouter Classifiers, потому что он размечает запросы прямо в LLM-потоке и дает аналитику по использованию.

## Сценарии использования

- Разметка AI-запросов и генераций по отделам, проектам, типам задач и стоимости.
- Аналитика использования LLM: кто, зачем и сколько тратит на AI.
- Классификация статей базы знаний по темам, продуктам, аудитории и уровню сложности.
- Поиск устаревших, дублирующихся или неполных материалов в документации.
- Автоматическая модерация пользовательского контента: спам, токсичность, персональные данные, запрещенные темы.
- Маршрутизация тикетов поддержки по категориям: баг, биллинг, настройка, интеграция, срочно.
- Разметка документов: договоры, счета, ТЗ, политики, инструкции, внутренние регламенты.
- Управление доступом и рисками: публичное, внутреннее, конфиденциальное, персональные данные.
- Построение отчетов по контенту: какие темы растут, какие продукты чаще упоминаются, где больше ручной проверки.
- Автоматизация действий: отправить на ревью, обновить, объединить, архивировать, передать в нужную команду.

## Ключевые составляющие системы

- **Цель классификации** — зачем нужна разметка: поиск, аналитика, модерация, маршрутизация, контроль затрат или governance.
- **Таксономия** — список категорий и правил: темы, типы материалов, продукты, аудитории, уровни, статусы.
- **Формат результата** — лучше JSON или другой структурированный формат, а не свободный текст.
- **Single-label или multi-label** — один класс на объект или несколько тегов одновременно.
- **Confidence score** — показатель уверенности модели, чтобы отделять автоматические решения от спорных.
- **Human review** — ручная проверка для низкой уверенности, чувствительных данных и пограничных случаев.
- **Gold set** — эталонный набор заранее размеченных примеров для проверки качества.
- **Версионирование схемы** — хранение версии таксономии, промпта, модели и результата классификации.
- **Интеграция с хранилищем** — CMS, база знаний, Notion, CRM, DWH, логи AI-запросов или BI.
- **Действие после классификации** — отчет, фильтр, алерт, задача, маршрутизация, публикация, архивация.

Пример результата классификации для базы знаний:

```json
{
  "content_type": "guide",
  "primary_topic": "content classification",
  "product": "OpenRouter",
  "audience": "developer",
  "intent": "learn",
  "sensitivity": "public",
  "recommended_action": "publish",
  "confidence": 0.86
}
```

Пример результата классификации AI-генерации:

```json
{
  "department": "marketing",
  "task_type": "article_draft",
  "project": "knowledge_base",
  "complexity": "medium",
  "sensitivity": "public",
  "cost_center": "content",
  "human_review_required": false,
  "confidence": 0.91
}
```

## Подборка сервисов и инструментов

### 1. OpenRouter Classifiers

**Для чего:** классификация AI-генераций, аналитика использования LLM, учет затрат, разметка запросов по отделам, задачам, проектам и compliance-категориям.

OpenRouter Classifiers автоматически запускает классификатор поверх LLM-генераций и добавляет к ним структурированные метаданные. Можно размечать запросы по собственным измерениям: department, task type, complexity, sensitivity, cost center, project и другим категориям.

**Особенности:**

- классификация выполняется асинхронно после основного запроса;
- не добавляет задержку пользователю;
- теги попадают в логи;
- агрегированная отчетность доступна в Activity;
- можно использовать собственную таксономию;
- удобно для AI governance и контроля расходов.

**Сильная сторона:** лучший вариант, если нужно понять, как именно в компании используются LLM.

**Ограничение:** инструмент сфокусирован на AI-генерациях, а не на произвольной CMS или базе знаний.

**Пример применения:**

```json
{
  "department": "support",
  "task_type": "customer_reply",
  "complexity": "low",
  "sensitivity": "internal",
  "cost_center": "support"
}
```

---

### 2. AWS Comprehend / AWS AI Services

**Для чего:** классификация текстов, анализ пользовательских сообщений, модерация, entity extraction, sentiment analysis, обработка документов.

**Особенности:**

- подходит для enterprise-пайплайнов;
- хорошо встраивается в AWS-инфраструктуру;
- можно обрабатывать большие объемы текста;
- применимо к чатам, опросам, тикетам, документам и пользовательскому контенту.

**Сильная сторона:** масштабируемая облачная обработка текста.

**Ограничение:** требует настройки архитектуры, данных и стоимости.

---

### 3. Microsoft SharePoint Taxonomy Tagging

**Для чего:** автоматическая разметка документов внутри Microsoft 365 и SharePoint.

**Особенности:**

- использует корпоративный term store;
- применяет managed metadata к документам;
- улучшает поиск, фильтрацию и управление файлами;
- хорошо подходит для библиотек документов.

**Сильная сторона:** нативная классификация документов в Microsoft 365.

**Ограничение:** привязка к SharePoint и экосистеме Microsoft.

---

### 4. ApyHub AI Text Content Classification API

**Для чего:** быстрая API-классификация текста в приложениях, продуктах и интеграциях.

**Особенности:**

- отправляете текст — получаете структурированный результат;
- удобно для routing, moderation и автоматической разметки;
- можно быстро подключить без собственной ML-инфраструктуры;
- подходит для прототипов и небольших сервисных интеграций.

**Сильная сторона:** простой API-подход.

**Ограничение:** качество нужно проверять на своих данных.

---

### 5. Quark Content Taxonomy

**Для чего:** управление структурированным корпоративным контентом, метаданными, таксономиями и переиспользованием материалов.

**Особенности:**

- фокус на enterprise content management;
- поддерживает metadata и content tagging;
- помогает искать, отслеживать, обновлять и переиспользовать контент;
- полезен для сложных документов и регулируемых отраслей.

**Сильная сторона:** сильная система для корпоративной таксономии и structured content.

**Ограничение:** избыточно для небольшого блога или простой базы знаний.

---

### 6. Собственный LLM-классификатор

**Для чего:** кастомная классификация под свою логику: база знаний, CRM, тикеты, комментарии, документы, AI-запросы.

**Как работает:**

1. Берем текст.
2. Отправляем в LLM с инструкцией и JSON-схемой.
3. Получаем категории, confidence и флаги.
4. Сохраняем результат в CMS, Notion, базе данных, логах или BI.

**Особенности:**

- максимальная гибкость;
- можно использовать любую таксономию;
- легко адаптировать под конкретный бизнес;
- можно совмещать классификацию, summary, extraction и scoring.

**Сильная сторона:** полный контроль над схемой и логикой.

**Ограничение:** нужно тестировать качество, обрабатывать ошибки и контролировать стоимость.

---

### 7. Hugging Face / spaCy / scikit-learn

**Для чего:** локальная или кастомная ML-классификация, когда важны контроль, приватность и стоимость на больших объемах.

**Варианты реализации:**

- zero-shot classification;
- fine-tuned transformer models;
- TF-IDF + logistic regression/SVM;
- spaCy pipelines;
- локальные модели для приватных данных.

**Сильная сторона:** контроль над моделью, данными и инфраструктурой.

**Ограничение:** требует ML/engineering-компетенций и обучающих данных.

## Быстрый выбор инструмента

- **OpenRouter Classifiers** — для аналитики AI-использования, затрат и разметки LLM-запросов по отделам, проектам и типам задач.
- **SharePoint Taxonomy Tagging** — для классификации документов внутри Microsoft 365 и автоматического применения корпоративных терминов.
- **ApyHub** — для быстрого API-сценария: отправить текст и получить классификацию без собственной ML-инфраструктуры.
- **Quark** — для enterprise-таксономии, structured content и управления большим объемом корпоративных материалов.
- **AWS Comprehend / AWS AI Services** — для масштабной обработки текстов, тикетов, сообщений и документов в AWS-инфраструктуре.
- **Собственный LLM-классификатор** — когда нужна гибкая логика, своя JSON-схема и полный контроль над правилами классификации.
- **Hugging Face / spaCy / scikit-learn** — для локальной ML-классификации, приватных данных и оптимизации стоимости на больших объемах.

## Короткий вывод

Если задача связана с AI-запросами и аналитикой использования LLM, первым стоит смотреть на **OpenRouter Classifiers**: он уже находится рядом с генерациями, добавляет структурированные метки и помогает видеть usage, cost и task taxonomy.

Если нужно классифицировать документы, статьи, тикеты или пользовательский контент, выбор зависит от инфраструктуры:

- Microsoft 365 → SharePoint Taxonomy Tagging;
- AWS → AWS Comprehend / AI Services;
- быстрый API → ApyHub;
- enterprise content management → Quark;
- полный контроль → собственный LLM- или ML-классификатор.

Главное правило: классификация должна не просто добавлять теги, а запускать полезное действие — поиск, отчет, фильтр, ревью, маршрутизацию или автоматизацию.
